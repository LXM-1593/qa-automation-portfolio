# 测试策略与分层设计（Test Strategy）

> 本文说明本作品集"为什么这样测"：范围边界、分层依据、设计方法落地位置、数据与环境策略、
> 出入口准则、缺陷分级、CI 触发与阻塞规则、度量基线、风险登记。
> 用例明细见 `docs/test-cases.md`（UI-001~015）与 `docs/api-test-cases.md`（API-001~018）。

---

## 1. 目标与范围

**目标**：以最小可维护成本，覆盖一条完整电商购买链路的用户价值，以及一组真实 REST 接口的契约正确性与异常健壮性。

| 范围内（In Scope） | 范围外（Out of Scope） | 理由 |
|---|---|---|
| 登录鉴权（成功/失败/锁定/登出） | 密码找回、注册、多因素认证 | SauceDemo 未提供，且非核心购买链路 |
| 商品列表与三种排序 | 商品详情页、搜索、筛选 | 演示站功能有限；排序已能验证列表数据一致性 |
| 购物车增删与角标联动 | 优惠券、库存并发扣减 | 无此业务 |
| 结算端到端（信息填写 → 概览 → 完成） | 支付网关真实扣款 | 演示站不接入真实支付 |
| 对象 CRUD + 404/400 异常契约 | 鉴权、限流、审计日志 | 目标 API 无鉴权设计（见 SEC-001） |
| 已确认缺陷的契约化回归（DEF-001~007） | 性能/压力/安全渗透 | 属独立测试类型，本项目不冒充覆盖 |

**明确不做的事**：不把"公开演示站"的测试结果包装成生产结论；不虚构未执行的用例结果。

## 2. 分层策略

测试金字塔在本项目做了**变形**：被测对象是第三方服务，没有源码可做单元测试，因此**接口层承担了原属单元层的大部分职责**（快速、稳定、定位精确），UI 层只保留业务价值的端到端验证。

| 层级 | 载体 | 数量 | 目的 | 执行耗时 | 失败含义 | 是否阻塞 |
|---|---|---|---|---|---|---|
| 接口契约层 | `postman/collection.json` 01–03 | 11 请求 / 29 断言 | 契约正确、CRUD 幂等、异常可预期 | ~15 s | 服务契约变更或缺陷 | **是** |
| 接口缺陷层 | 同上，04 文件夹 | 6 请求 | 把已知缺陷固化为断言，修复即转绿 | ~8 s | 失败 = 缺陷仍存在（**预期行为**） | 否（`continue-on-error`） |
| UI 端到端层 | `tests/`（Pytest + Selenium） | 15 用例 | 用户视角的购买链路可用性 | ~160 s | 前端功能回归 | **是** |

**分层配比理由**：UI 用例慢且脆（受渲染、网络、动画影响），因此只放"不可替代的用户路径"（P0/P1）；
字段级校验、状态码语义、错误体结构这类"多而细"的检查全部下沉到接口层——同样的问题在接口层发现，定位成本低一个量级。

## 3. 覆盖矩阵

### 3.1 业务流 × 层级

| 业务流 | UI 用例 | 接口用例 | 覆盖判断 |
|---|---|---|---|
| 登录鉴权 | UI-001~004 | — | UI 全覆盖（含锁定用户这一非常规分支） |
| 商品浏览与排序 | UI-005~008 | — | UI 覆盖；排序以"序列单调性"断言，不比对固定文案 |
| 购物车状态迁移 | UI-009~012 | — | 覆盖 0→1→2→1→0 四个状态转换 |
| 结算与校验 | UI-013~015 | — | 基本流 + 必填项拦截 + 金额展示 |
| 对象 CRUD | — | API-001~008 | 全链路，含删除后 404 验证 |
| 异常与边界 | UI-002/003/014 | API-009~018 | 不存在 id、非法 JSON、缺失/空/错类型字段 |

### 3.2 优先级分布

| 优先级 | UI | 定义 |
|---|---|---|
| P0 | 4（UI-001/005/009/013） | 主流程断链，用户完全无法完成购买 |
| P1 | 8 | 重要分支或数据正确性受损 |
| P2 | 3 | 展示类、体验类 |
| P0 接口 | API-001/003/007 | 读、创建、删除三类核心动作 |

## 4. 测试设计方法的落地位置

设计方法不是"写在文档里"的，每条都能指到具体用例：

| 方法 | 应用点 | 具体用例 |
|---|---|---|
| **等价类划分** | 登录账号分三类：合法（standard）、凭证错误、状态异常（locked） | UI-001 / UI-002 / UI-003 |
| **等价类划分** | `name` 字段：合法字符串、缺失、空串、非字符串 | API-003（有效） / DEF-001 / DEF-002 / DEF-003 |
| **边界值分析** | 必填项取"空"这一下边界（非空即有效，故只需测空） | UI-014 |
| **边界值分析** | 资源标识：存在 id vs 不存在 id | API-009 / API-010 |
| **场景法** | 基本流：登录→选品→加购→结算→完成；备选流：缺邮编中断 | UI-013（基本流） / UI-014（备选流） |
| **状态迁移** | 购物车计数状态机 0→1→2→1→0，验证每次迁移的角标 | UI-009 / UI-010 / UI-011 |
| **错误推测** | 依据经验优先攻"开发者最容易漏的守卫"：非法 JSON、类型强转、空值落库 | API-011 / DEF-002 / DEF-003 |

**未采用的方法及原因**：正交试验（因子少，组合爆炸无收益）、因果图（判定逻辑简单，判定表即可）、
模糊测试（目标是契约验证而非漏洞挖掘）。

## 5. 环境与数据策略

| 关注点 | 策略 |
|---|---|
| 环境 | 唯一环境：公开演示站 + 公开 API。无 staging，因此**不写死易变数据**（商品数量、记录总数随时间/他人操作变化） |
| 数据构造 | UI：账号数据外置在 `test_data/users.json`，不硬编码进用例 |
| 数据清理 | 接口：每个创建动作后在同一链路内删除；集合内 `objectId` 变量随请求流转，避免跨用例隐式依赖 |
| 用例独立性 | UI：每个用例新建浏览器会话 + 独立 `user-data-dir`，结束后销毁，可任意顺序、重复执行 |
| 时序稳定 | 不使用固定 `sleep`；统一 `WebDriverWait`，排序场景额外等待 DOM 顺序稳定 |
| 共享环境干扰 | 断言只校验**结构与契约**（字段存在、状态码、错误体关键字），不校验他人在共享实例上的数据 |
| 配额约束 | 目标 API 每 24h 限 50 请求，超限返回 405（DEF-007）。因此 API 层不在每次 push 时无条件执行，见第 8 节 |

## 6. 入口准则与出口准则

### 入口（满足才开跑）

- 目标站点 / API 可访问（连通性探测返回 2xx/4xx 而非超时）；
- 依赖已安装，浏览器与驱动版本匹配（Selenium Manager 自动解析）；
- 接口配额未耗尽（否则结果无意义，应先等待重置）。

### 出口（满足才算通过）

| 层级 | 出口条件 |
|---|---|
| UI | 15/15 通过；无 flaky（连续两次执行结果一致）；失败用例必须附截图与堆栈 |
| 接口稳定层 | 29/29 断言通过，0 请求级错误（连接失败/超时） |
| 接口缺陷层 | 6 条按预期失败；若某条转绿，说明缺陷已修复 → 更新缺陷状态并从回归集移除 |
| 整体 | 无 P0/P1 级未关闭缺陷；已知缺陷均有编号、证据与影响说明 |

## 7. 缺陷管理

### 严重程度定义

| 级别 | 判定标准 | 本项目实例 |
|---|---|---|
| **S1 / Critical** | 主流程不可用、数据丢失或安全泄露 | 无 |
| **S2 / High** | 核心校验缺失导致脏数据落库；或绕过业务约束 | DEF-001（缺 `name` 落库为 null）、DEF-002（空串被接受） |
| **S3 / Medium** | 契约不符但可绕过，或错误语义误导调用方 | DEF-003（类型静默强转）、DEF-007（超限 405 非 429） |
| **S4 / Low** | 语义偏差、文案不一致，无功能影响 | DEF-004（201→200）、DEF-005（404 文案）、DEF-006（204→200） |
| **Info** | 设计观察项，非缺陷 | SEC-001（无鉴权） |

### 缺陷单必填字段

严重程度、优先级、状态、前置条件、复现步骤、预期结果、实际结果、证据（真实响应转录）、影响、修复建议。
**"实际结果"必须来自真实调用**（`reports/api-smoke.json` 或 Newman 执行输出），不允许推测填写。

### 严重程度 ≠ 优先级

严重程度衡量**影响**，优先级衡量**修复顺序**。例：DEF-007 严重程度 Medium，但因影响所有调用方的限流判断，
优先级可提到 P1；DEF-006 语义偏差影响面小，优先级 P3。

## 8. CI 集成策略

| 触发 | UI 回归 | 接口稳定层 | 接口缺陷层 | 说明 |
|---|---|---|---|---|
| push / PR 到 `main` | ✅ 阻塞 | 仅当 `postman/**` 变更 | 否 | 避免每次提交都消耗 API 配额 |
| 手动 `workflow_dispatch` | ✅ | ✅ | 可选 | 用于发版前全量验证 |
| 每周定时（周一 09:00） | ✅ | ✅ | 否 | 捕获演示站/服务端静默变更 |
| 含 `[skip ci]` 的提交 | 跳过 | 跳过 | — | 纯文档改动不触发 |

**设计取舍**：
1. **API 层不做"每次 push 必跑"**——公开实例 50 次/天的配额会被 CI 瞬间耗尽，反而制造假红。改用路径过滤 + 定时。
2. **缺陷层永不阻塞**——它失败代表"缺陷仍在"，是预期状态；若改成阻塞，团队会习惯性忽略红灯（告警疲劳）。
3. **失败必须可诊断**——UI 失败自动截图并上传 `reports/`，接口失败上传 Newman JSON 报告，避免"红了但不知道为什么"。

## 9. 度量基线

| 指标 | 当前值 | 采集方式 | 用途 |
|---|---|---|---|
| UI 用例通过率 | 15/15 = 100% | pytest 汇总 | 功能健康度 |
| UI 执行时长 | ~160 s | pytest `--durations` | 判断是否该拆分/并行 |
| 接口断言通过率 | 29/29 = 100%（稳定层） | Newman summary | 契约健康度 |
| 用例有效率 | 15 UI + 18 API，全部可执行、无跳过 | 用例库盘点 | 防止"僵尸用例" |
| 缺陷密度 | 7 缺陷 / 29 接口断言 ≈ 0.24 | 缺陷报告 | 衡量测试有效性 |
| Flaky 率 | 0（连续两次执行结果一致） | 重复执行 | 判断用例可信度 |

> 这些数字只描述**本次执行时点**的真实状态，不作为长期能力宣称。

## 10. 风险登记

| 风险 | 影响 | 概率 | 缓解措施 |
|---|---|---|---|
| 演示站前端改版，定位器失效 | UI 套件批量红 | 中 | 选择器集中在 `pages/`；失败截图 + 显式等待报错信息可直接定位 |
| 公开 API 配额耗尽（50/天） | 接口层假红 | 高 | CI 路径过滤 + 定时；本地跑前先探连通性；文档标注 DEF-007 |
| 共享实例数据被他人改动 | 断言偶发失败 | 中 | 只断言结构不写死数量；自造数据自清理 |
| 第三方服务不可用 | 全量红且无法区分"服务挂了"与"我们写错了" | 低 | 失败先看是超时还是断言失败，二者归因不同 |
| 无鉴权导致测试数据被误删 | 用例中途 404 | 低 | 单用例内自造自清，不跨用例复用 id |
| 单一浏览器（Chrome）覆盖 | 跨浏览器缺陷漏检 | 确定存在 | 明确列为范围外，不宣称兼容性覆盖 |

## 11. 后续演进方向

1. **补充单元层**：若引入自有后端，对业务规则做纯函数级单测，把当前压在接口层的校验下沉。
2. **契约测试**：用 JSON Schema 固化响应结构，替代手写字段断言，降低维护量。
3. **跨浏览器矩阵**：接入 Playwright 或 Selenium Grid，覆盖 Firefox / WebKit。
4. **可视化回归**：对结算页做截图比对，捕获纯样式回归。
5. **缺陷闭环自动化**：缺陷修复后自动将 04 文件夹对应断言转入 03 稳定层。
